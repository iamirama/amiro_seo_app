Project: Build a Professional SEO Audit and Analysis Web Application 

1. Project Overview

Without asking any questions، Build a modern, professional, and user-friendly web application that performs comprehensive SEO audits for any publicly accessible website.

The application must connect to multiple reputable SEO services, search engine tools, website performance analyzers, and technical SEO utilities.

Its primary purpose is to identify SEO problems, explain why each problem matters, provide actionable instructions for fixing it, and generate a comprehensive HTML report that users can download and share.

The application should support both free tools and paid services with API access.

Prioritize free services and free API tiers wherever possible. However, do not assume that a service offers a free API simply because its website or browser-based tools are free.

The application must clearly distinguish between:

- Free services with usable APIs.
- Services with limited free API quotas.
- Paid services requiring a subscription or API credits.
- Tools that can be used without an API key.
- Services that are configured but not connected.
- Services that are connected but lack sufficient permissions or available credits.

Do not build a fake demonstration of API connectivity. All connection tests, scans, and reports must reflect real results.

If a service is unavailable, explain the problem clearly and use other successfully connected services when appropriate.

5. Mandatory API Validation Before Scanning

This is one of the most important requirements.

The application MUST validate configured API connections before beginning a scan.

Implement a mandatory pre-scan validation workflow.

Step 1: User Starts a Scan

The user enters a website URL and clicks "Start SEO Audit."

Before starting the scan, the application identifies which integrations are:

- Required for the selected scan.
- Optional enhancements.
- Configured and connected.
- Missing credentials.
- Not yet validated.
- Failing authentication.
- Failing because of rate limits, quota exhaustion, or insufficient permissions.

Step 2: Validate All Selected Services

Run a real connection test for every selected provider that is required for the scan.

Use the provider's documented authentication or lightweight API endpoint.

Do not validate an API merely by checking whether an API key field is populated.

A successful test must establish that the service is reachable and that the credentials are accepted for the relevant operation.

Where possible, verify that the configured account has the permissions and credits needed for the selected scan.

If a provider does not offer a lightweight validation endpoint, use the safest appropriate documented request.

Do not make expensive API requests just to test connectivity.

Step 3: Display Validation Results

Show a validation summary containing:

- Provider name.
- Connection status.
- Authentication status.
- Permission status, when verifiable.
- Quota status, when available.
- Error message, if applicable.
- Suggested corrective action.

Use clear status labels:

- Connected.
- Connected with limitations.
- Authentication failed.
- Permission denied.
- Rate limited.
- Quota exhausted.
- Service unavailable.
- Not configured.
- Validation inconclusive.

Never label a connection as successful if the response is ambiguous.

Step 4: Enforce the Pre-Scan Gate

If the user has selected one or more required services and any of them fail validation, do not start the scan.

Show which services failed and explain how to fix the problem.

Provide a "Retry Validation" button.

Allow the user to return to Settings and correct the credentials.

The application must not silently skip a required service.

However, users should be able to select which providers are required for each scan.

Optional services may fail without blocking the entire scan, provided at least one valid scan method remains available.

For example:

- If Google PageSpeed Insights is required and its validation fails, do not begin that scan.
- If Ahrefs is optional and its API is unavailable, allow the scan to proceed using the remaining validated sources, but clearly mark backlink analysis as unavailable.
- If no valid scan method is available, block the scan completely.

Step 5: Revalidate When Necessary

Do not assume that a previous successful test guarantees future API availability.

Check authentication and service availability when starting a scan, and handle token expiration, rate limits, and other failures during execution.

If a provider fails midway through a scan, record the failure, preserve completed results, and clearly mark the affected report sections as incomplete.

6. Website Scanning Engine

Implement a configurable website crawler.

The user should be able to enter:

- Website URL.
- Scan scope.
- Maximum number of pages.
- Maximum crawl depth.
- Request timeout.
- Crawl concurrency.
- Whether external links should be checked.
- Whether subdomains should be included.
- Whether query parameters should be included.
- Whether robots.txt rules should be respected.
- Whether sitemap URLs should be used as crawl seeds.

Provide sensible default limits to avoid overwhelming websites.

Normalize URLs and prevent duplicate crawling of equivalent URLs.

Respect robots.txt directives and website crawl policies.

Use an identifiable crawler User-Agent.

Implement request throttling, retry limits, timeouts, and safe redirect handling.

Do not bypass authentication, CAPTCHAs, access controls, or anti-bot protections.

Only crawl publicly accessible pages that the application is permitted to access.

Prevent server-side request forgery (SSRF). Block requests to localhost, private IP ranges, link-local addresses, cloud metadata endpoints, and other prohibited destinations. Revalidate DNS and redirect destinations to prevent bypasses.

Restrict protocols to HTTP and HTTPS.

Protect against DNS rebinding and redirect-based access to internal services.

Implement crawl cancellation and progress tracking.

Show:

- Pages discovered.
- Pages crawled.
- Pages remaining.
- Errors encountered.
- Current scan stage.
- Estimated progress, when it can be calculated reliably.

Do not display invented progress percentages or estimated completion times without a reasonable basis.

7. Comprehensive SEO Audit

Organize the audit into the following categories.

A. Technical SEO

Check for:

- HTTP errors.
- Broken internal links.
- Broken external links, if enabled.
- Redirect chains.
- Redirect loops.
- HTTP-to-HTTPS problems.
- Mixed content.
- robots.txt issues.
- Sitemap errors.
- Incorrect canonical tags.
- Duplicate canonical URLs.
- Pages blocked by robots directives.
- Missing or conflicting indexability directives.
- Incorrect HTTP status codes.
- Missing security-related headers where relevant.
- Hreflang errors.
- Duplicate URL variations.
- Orphan pages when sufficient data is available.
- Incorrect internal links.
- Excessively deep pages.
- Server response problems observable from the crawler.

B. On-Page SEO

Check for:

- Missing title tags.
- Duplicate titles.
- Titles that may be excessively long or short.
- Missing meta descriptions.
- Duplicate meta descriptions.
- Heading hierarchy issues.
- Missing H1 headings.
- Multiple H1 headings where potentially problematic.
- Missing image alt attributes.
- Oversized images where measurable.
- Poor internal linking.
- Missing canonical tags.
- Missing Open Graph metadata.
- Invalid or incomplete structured data where detectable.

Treat length thresholds as configurable heuristics, not universal ranking rules.

C. Content SEO

Analyze:

- Thin or low-information pages.
- Duplicate or near-duplicate content.
- Keyword targeting conflicts where sufficient keyword data exists.
- Missing topical coverage.
- Repeated content patterns.
- Content readability.
- Heading organization.
- Descriptive URL structure.
- Content freshness signals when available.
- Internal linking opportunities.
- Pages with insufficient contextual information.

Do not label content as AI-generated without reliable evidence.

Do not claim that a particular word count guarantees rankings.

Clearly distinguish automated heuristics from verified facts.

D. Performance and Core Web Vitals

Use PageSpeed Insights and Lighthouse data where available.

Analyze:

- Largest Contentful Paint (LCP).
- Interaction to Next Paint (INP).
- Cumulative Layout Shift (CLS).
- First Contentful Paint (FCP).
- Total Blocking Time (TBT).
- Speed Index.
- Image optimization.
- JavaScript execution.
- CSS optimization.
- Render-blocking resources.
- Unused JavaScript and CSS opportunities.
- Caching opportunities.
- Font-loading issues.

Clearly distinguish real-user field data from laboratory measurements.

If field data is unavailable, state that explicitly.

Do not substitute laboratory measurements for real-user Core Web Vitals without explaining the difference.

E. Backlink Analysis

Use Ahrefs, Moz, or other configured providers where access is available.

Analyze supported metrics such as:

- Referring domains.
- Backlink counts.
- Linking page information.
- Anchor text.
- New and lost backlinks when supported.
- Link attribute information when available.
- Referring domain quality indicators.

Do not pretend that a partial backlink index represents the entire web.

Do not label backlinks as toxic or harmful solely because of an arbitrary metric.

When backlink data is unavailable, mark the section as unavailable and explain how to connect a supported provider.

F. Keyword and Search Visibility

Use Search Console, Bing Webmaster Tools, and configured commercial APIs.

Analyze:

- Search queries.
- Impressions.
- Clicks.
- CTR.
- Average search position.
- Pages receiving organic search traffic.
- Keyword opportunities.
- Pages with high impressions and relatively low CTR.
- Queries where relevant pages appear to have improvement opportunities.
- Potential keyword cannibalization when sufficient evidence exists.

Never invent keyword rankings, search volumes, or traffic estimates.

Every metric must include its source and, where relevant, its date range and geographical scope.

- getProviderMetadata()

20. Final Acceptance Criteria

The project is considered successful only when the following conditions are satisfied:

1. A user can enter a valid website URL and configure a scan.
2. The application can perform a real technical SEO crawl.
3. The application can identify actual website issues.
4. Each finding includes evidence and actionable remediation guidance.
5. The user can configure API providers through Settings.
6. Every configured provider has a genuine connection-validation workflow.
7. Required services are validated before a scan begins.
8. Failed validation blocks the scan when the selected configuration requires that service.
9. Optional provider failures are clearly reported without unnecessarily blocking otherwise valid scans.
10. API errors, permission problems, and quota limitations are handled correctly.
11. The application does not fabricate API responses, metrics, or findings.
12. The user can generate and download a standalone HTML report.
13. The report clearly documents its data sources and limitations.
14. Scan history and scan comparisons work correctly.
15. API secrets remain protected on the backend.
16. The crawler includes robust SSRF protections.
17. The application works in a free-first configuration without requiring a commercial SEO subscription.
18. The project includes complete setup instructions and meaningful tests.

Begin by presenting a concise implementation plan, the proposed technology stack, and the provider capability matrix.

Then implement the application in working stages, starting with the free technical SEO crawler, secure Settings page, mandatory API validation workflow, and downloadable HTML reporting.

Prioritize real functionality, security, accuracy, and maintainability over visual complexity.
